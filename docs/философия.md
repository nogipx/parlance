# Философия parlance

parlance — язык, на котором части приложения говорят друг с другом, не зная друг друга. Это не фреймворк приложения и не хранилище: в нём есть слова, их владельцы и правила разговора, а решения и данные остаются у приложения.

Каждое новое предложение проверяется по принципам ниже. Если возможность противоречит принципу, её нет в parlance, как бы удобна она ни была для одного приложения.

## Принципы

**1. Слово — контракт.** Части говорят только словами. Слов четыре рода:

- **состояние** — что есть сейчас (`house.heat.target = 21`);
- **команда** — сделай (`house.light.set(room: kitchen, on: true)`);
- **запрос** — ответь, ничего не меняя (`orders.page(from: 20)`);
- **факт** — что случилось (`house.doorbell.rang(who: bob)`).

Слово объявляется один раз, абстрактным классом Dart (`@Vocabulary`). Генератор делает из него всё остальное: типы, базу владельца, клиента.

**2. У каждого слова один владелец.** Только он пишет состояние, обслуживает команду, отвечает на запрос, говорит факт. Остальные читают, слушают и просят командой. Словарь (`house.*`) принадлежит одному владельцу.

**3. Каждый действует от своего имени, и у каждого действия есть причина.** Действует принципал (`user/ann`, `house@devices`). Всё, что сделано в ответ на вызов или факт, следует из него само. Отсюда журнал и `explain`: кто сделал, вслед за чем, кто начал. Действовать от имени другого можно только явно и с правом на это (`speakFor`): причина тогда его, а не говорящего.

**4. Части не знают друг о друге.** Они знают только слова. Если слова нет, это его статус (`missing`), а не ошибка. Части запускаются в любом порядке, и ни одна не ждёт другую.

**5. Участник — это область жизни.** Участник (модуль, сессия пользователя, гость) приносит своих владельцев и их слова. Когда он уходит, уходит всё, что он принёс, и ничего не остаётся «последним известным».

**6. Одинаково везде.** Участник в процессе хоста и участник через соединение — один и тот же `IParticipant`. Владелец не знает, где он работает.

**7. Реестр решает только то, что говорит язык.** Типы значений, кто может читать и вызывать, доступна ли команда, правила (guard'ы) на вызовы своих команд. Всё остальное — политика приложения: кто сильнее правила, что хранить, когда что делать. Её пишет приложение, на словах.

**8. Без церемоний.** Разработчик пишет только то, что знает он один: слова и обработчики. Всё, что библиотека может сделать сама (причины, переподключение, запись после подключения, очистка), она делает сама.

**9. То, чего касается разработчик, не ломается.** `schema.dart` и `app.dart` только растут. Внутренности — реестр, протокол, зеркало — меняются свободно.

## Что из этого следует

| | Почему |
|---|---|
| Открытых фактов с несколькими «производителями» нет | п. 2: у факта один владелец. Если нескольким частям нужен общий факт, им владеет одна, а остальные просят её командой. |
| Переопределения запретов (`override`, `overriders`) нет | п. 7: «кто сильнее правила» — политика. guard сам решает, кого пропустить. |
| Значения не переживают своего владельца | п. 2 и 5: у значения без владельца нет хозяина, и его некому обновить. Что должно жить дольше, принадлежит тому, кто живёт дольше, или хранится самим приложением. |
| Хранения и кэша в реестре нет | п. 7: реестр показывает, что живые владельцы говорят сейчас. Журнал — отдельный пакет. |
| Варианты (`choices`, `@ChoiceOf`) есть | Это тип с меняющимся набором значений (п. 7): значение — одно из тех, что даёт владелец. Агенту и редактору они показывают, из чего выбирать. |
| `meta` и `@Describe` есть | Описания слов для людей и инструментов. Они ничего не решают. |
| Повтор по id (`once`, id вызова) есть | Одно и то же действие, пришедшее дважды, делается один раз. Это свойство разговора, а не приложения. |
| Агенты (MCP), правила «когда X — сделай Y» (`parlance_links`), журнал — отдельные пакеты | Это потребители слов, а не их язык. |
| Один реестр, один способ сделать одно дело | Лёгкий хост — это тот же `Host` с другими пределами (`HostBounds.light`), а не второй реестр. |

## Один путь

У каждого дела один способ (п. 8). Всё, что делает то же другим путём, уходит в библиотеку инструментов или удаляется.

| Дело | Путь |
|---|---|
| объявить слова | `@Vocabulary` — абстрактный класс; остальное делает генератор |
| владеть словами | `class Home extends HouseOwnerBase`: только обработчики и значения |
| пользоваться чужими словами | клиент `HouseClient(participant)` по интерфейсу `IHouseClient` |
| хост | `Host()` в `main` |
| часть приложения | `host.participant(who, ...)`, затем `.attach({...})` здесь или `.serve(endpoint)` через соединение |
| гость | `Guest.join(connection)` или `Guest.over(endpoint)` |
| запрет на вызов | `guard(...)` во владельце |
| тест | `TestHost` поверх того же `Host` |

Сгенерированный код живёт в пакете разработчика, поэтому то, что он вызывает, разработчик вызвать может. Для этого кода есть одна дверь — `GeneratedWords.of(participant)`. Это контракт генератора, а не способ писать руками. У самого участника нет ни типизированного доступа к словам, ни чтения и вызова по имени.

Чтение и вызов по имени, слова с именами, известными только во время работы, сам реестр — это инструменты: агент, журнал, инспектор, плагины на чужом языке. Они в одной незамороженной библиотеке.

## Чего в parlance нет и не будет

- поведения: «когда X, сделай Y» — это `parlance_links` или код приложения;
- хранения: persist, кэши, офлайн;
- ролей и систем прав сверх «кто может читать и вызывать это слово»;
- проекций, адаптеров и машинерии устаревания между версиями слов: старую версию обслуживает её владелец;
- состояния экрана: то, что не читает никто, кроме экрана, в реестр не кладётся.

## Как проверять новое предложение

1. Можно ли выразить это словами и владельцами, которые уже есть? Если да — это код приложения, а не библиотеки.
2. Не появляется ли у слова второй владелец, второй способ сделать то же или решение политики в реестре?
3. Нужно ли это любому приложению или одному конкретному? Если одному — этому приложению.
4. Пишет ли разработчик что-то, что библиотека могла бы сделать сама?
