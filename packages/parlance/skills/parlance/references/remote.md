# parlance contract: remote (§14)

Part of the contract the code and its tests follow; sections keep their numbers across these files (`SPEC §n` in the code), and SKILL.md maps them. Where code and contract disagree, the contract is fixed first.

## 14. Remote

In Dart the participant's side is one class, `RemoteParticipant` (§22): the client, the owner service and the mirror below are the package's own, and this section is the protocol they speak, what a part in another language would speak too.

Two peer services over one connection (`RpcPeerEndpoint` on both sides), generated by `rpc_dart_generator` from annotated interfaces (`lib/src/remote/contract.dart`); every method has codecs, so they run over any transport. The registry's side serves `Parlance` (a `RemoteSession`, `participant.serve(endpoint)`); the participant's side serves `ParlanceOwner` when its session owns commands.

| Method | Kind | Does |
|---|---|---|
| `describe` | unary | the catalog as the session's principal sees it (`Registry.describeFor`: with what it may call and what cannot run now), the protocol's major and the features the host speaks |
| `feed(epoch?, since?)` | server stream | the catalog as `describe` gives it, first and on every catalog change; then the feed of §12, as the session's subscription carries it; and after a tick that changes which commands cannot run, the whole set of them (`unavailable`) |
| `subscribe(states?, facts?)` | unary | what the session's feeds carry: these states and facts, or all of them (null); answers the subscription's number |
| `call(id, command, params, override, test, parent?)` | unary | a call on behalf of the session's principal |
| `why(state, key?)` | unary | `Registry.explain` as an `Explanation` |
| `recent(fact, count)` | unary | the last facts of a name the registry keeps |
| `define(descriptor)` | unary | a state, a command or a fact of the session's own, as far as the host lets it |
| `undefine(name)` | unary | withdraws a word the session defined |
| `set(state, key?, value, remove, parent?, test)` | unary | writes a state the session owns |
| `emit(fact, payload, id?, by?, parent?, test)` | unary | says a fact the session owns, or an open one it produces; `by` when it speaks for someone |
| `apply(ops)` | unary | what a remote participant asked (§22.4), in order, as one tick: `define`, `undefine`, `set`, `remove`, `emit`, `available`, `kind`, `unkind`, `guard`, `unguard`, `built` (what it was built against, §6.9: `prints`, each word's fingerprint, answered `{unknown: [word]}` for those the host does not know; `words`, schemas by name; `from`, the words package), `unbuilt`; an answer per op, a refusal of one not stopping the rest: an op that is not one (a field of the wrong type, a name that is no name, an `as` or `by` that is no principal) is refused alone, `invalidArgument`, as a call's or an emit's such `as` or `by` is |

`ParlanceOwner`, the participant's side:

| Method | Kind | Does |
|---|---|---|
| `serve(id, command, params, cause)` | unary | serves a call of a command the session owns; answers its value or why it failed |
| `judge(guard, id, command, params, cause)` | unary | asks a guard of the session's about a call of its command; answers why not, or nothing |

- **A session is one connection with one principal**, fixed by the host when it accepts the connection: the host makes a participant for it, as for a module in this process (who it is, its vocabularies, its rights), serves it on the connection's endpoint (`participant.serve(endpoint)`, a `RemoteSession`) and `close()`s the session when the connection ends. The words it defined go with it; its calls are refused after, and its feeds end, so nothing more goes to a session the host closed with its connection still up. A feed asked from a seq of another run (another epoch) starts with a snapshot, however a slow client held it back.
- **A session is a participant** (§22): `describe` tells it its principal, its `vocabularies` and its access by default (`defaults`: `read`, `call`), as the host made the participant it serves. **It may own words in its vocabularies, as far as the host lets it** (the participant's `ParticipantRights`): `define` (a further check by descriptor: callers that name viewers), `produce` (which open facts of others it says) and `speakFor` (on whose behalf it says a fact: the fact's cause is theirs, so what is done for it is done with those rights). Without rights a session only calls. A remote owner is an owner like any other: its states have one writer, the session; its commands one handler, the participant's, which the registry calls over the same connection with the call's cause; a handler that throws fails the call with its message, a lost connection fails it too. Past its deadline the call is `timedOut`, as in the host's process, and the owner's late end is still waited for (`RemoteSession.lateEnds`, five minutes) and recorded `late`.
- **What a session does follows from what it answers.** `parent` on `call`, `set` and `emit` names a call the session is serving (its id) or a fact the registry still keeps (its id): the cause is that message's child, so the journal says why. An unknown parent starts a new chain.
- **A call's result is data, not an error.** `done`, `refused` (with the code, the reason, the guard and whether it is overridable), `failed`, `timedOut` travel as the reply, because a refusal is a normal answer and carries more than a status code. rpc_dart statuses are for the session's own errors: `notFound` (no such state or fact), `invalidArgument` (a value or a descriptor of the wrong type), `permissionDenied` (the principal may not set that state, define that word, write a state it does not own, produce that fact or speak for that principal), `alreadyExists` (a name defined already), `unavailable` (the session ended).
- **A call answers the epoch and seq** the registry had when it answered. A mirror that reached that seq (its `reach`) shows what the call wrote: a read after a call reads its effect, as it does in the registry's own process. A call goes after the participant's pending subscription, so what it writes of what its listeners watch comes back on the feed; and when the ticks up to its seq carry nothing the session follows, the feed tells they went by with an empty tick, so the call returns at once rather than wait for a tick it is never sent.
- **A subscription is bounded:** one naming more than `serve(endpoint, maxSubscription:)` (4096) states and facts is refused (`resourceExhausted`).
- **A lost answer is a result, `lost`.** When the connection breaks before the answer, the call answers `CallLost` with the call's id (it always sends one) rather than throwing: whether it ran is unknown, and a retry with the id runs it at most once. The session's own refusal of a call is no lost answer: an `as` that is no part of it is `refused` (`notPermitted`), its other statuses (§14 above) `failed`.
- **A mirror keeps only what the catalog has**: the values of a state that left it go when the catalog says so, though no tick removed them.
- **Ids are per principal.** The registry sees a call's id, and a fact's, as `<principal>#<id>`: a client that lost its connection retries with the same id and gets the first result; another principal reusing the id does not.
- **A client sets no part of a cause** but its `parent`; who it is the session says.
- **Logs** (§9.2). A session logs to `serve(endpoint, log:)`, else the registry's `sessions`, with its id and principal: when it opens and ends, and what it was denied. `RemoteParticipant.join(connection, log:)` logs how its connection goes (joined, offline, joined again), what the host refused (`warning`), and a span for each call it serves, in the host's trace; `LogScope.noop` unless given. RPC telemetry goes on the endpoints: the host's is its own before it serves it; `join(connection, interceptors:)` puts them on the one it makes, before its first call (`over` takes one made elsewhere). Both sides are peers, so an OTel pair goes on each (`OtelRpcInterceptor` takes the calls the endpoint serves, `OtelRpcClientInterceptor` those it makes), with `where:` leaving out `feed`, one stream as long as the session.
- **Deadlines.** A call has no deadline of the client's: the registry bounds it itself (the handler by the command's deadline, an asked guard by its timeout) and answers `timedOut`. The other requests are answered at once and wait the client's `timeout` (10 s).
- **A subscription leaves out what it may not read**, rather than being refused: one such word among what a participant's listeners ask for would otherwise hold back every word added after it. The answer lists them (`left`); the word's status says why (§6.5).
- **The protocol grows, it does not break.** Its major (`parlanceProtocol`, 1) is what both ends must share and does not change; what is added comes as a **feature**, a name the host lists in `describe` (`features`; `parlanceFeatures` of its build, fewer given to `serve(features:)` stand in for an older host in a test). A name keeps its meaning for good: a change is a new name beside it; a name goes when nothing needs it, and a host stops listing it.
  - A participant uses a feature only when the host listed it: what it would send of one the host lacks it does not send (what it was built against, `built`, is kept and told to a later session that speaks it). Guests over the air are often built against a newer parlance than their host; the newer end is the one that adapts.
  - `join` and `over` take `requires`, the features a participant cannot do without. A host of another major, or one lacking a required feature, is refused (`ProtocolMismatch`, saying the majors or `missing`), on joining and on joining again; a feature merely missing is no refusal.
  - What an end does not know it passes over: a feature, a field, a kind of feed item; an op of `apply` it does not know is refused alone.
  - So does a participant with what a newer parlance adds to the language, as a host does not know what its guests speak: a type it does not know is an `UnknownType`, kept as it came (the rule finds it another type than the code holds, a `WordMismatch`, and a value of it is the host's to check); an access it does not know is `deny`, the least it may mean, in a word's callers or the defaults told at join; a kind of word it does not know is no word to it. A registry, which must check values, takes no word of a type it does not know (`unknownTypeIn`; across a connection, that op is refused, `invalidArgument`).
- **The wire's errors stay inside.** A remote participant answers as one in the host's process: `explain` of a state there is not is an empty explanation, `recent` of a fact there is not or it may not hear is empty, a refusal is `NotPermitted`; a host it cannot reach is `RegistryUnreachable`.
- **A session's feeds carry what it subscribed to.** Until it subscribes, everything, as before protocol 4. After, a snapshot has only the states it names, a tick only their changes and the facts it names; a tick with nothing of them is not sent, and the next one sent starts right after the last one sent (`from`), so the ticks stay without gaps. Subscribing again replaces it: each open feed gets a `values` item with the values of the states it carries now and did not, and which it carries (`keep`), so a copy drops the others; that item and the snapshots after carry the subscription's number, so a participant knows when its feed follows it. The subscription is the session's, and so is what the host knows from it: `RemoteSession.hears(test)` (whether its feeds carry a fact that matches, or it read the recent of one), for what a participant learns of viewers.
- **A slow client does not make the host hold its backlog.** The connection applies backpressure (rpc_dart pauses a stream while its send waits for the client's window), so a feed whose client takes less than the registry says holds what waits, up to `feedBacklog` items (`serve(endpoint, feedBacklog:)`, 256 by default). Past it, the ticks held are dropped (the catalog and the availability last told and a subscription's values stay), and when the client takes more the feed follows again from the last seq it sent, as the registry's `feed(since:)` has it: the ticks the registry still retains, with no gap and no fact lost, or a snapshot of now that says `factsLost`.
- **A word's `readers` (§6.1, §6.3) bound what a session sees of it.** A state it may not read is left out of its snapshots, ticks (the next tick sent still starts right after the last one sent), `values` items; a fact it may not hear, out of its ticks; `subscribe` naming either, `why` of the state and `recent` of the fact answer `permissionDenied`, and such a fact is no `parent` of what it does.
- **Word status over remote** (§6.5). The feed's catalog says what the session's principal may call and read and which commands cannot run; an `unavailable` item follows a tick that changes the latter, whether or not the tick itself is sent. The mirror answers `statusOf(name)` from them and tells `statusChanges` when either moves; while cut off it answers what it had last. Protocol 5: a client skips a feed item of a kind it does not know. Protocol 6: `apply`, `judge`, and `describe` with the principal and namespaces. Protocol 7: an op of `apply` and a `call` may carry `as`, a part of the session's principal (§22.3); the host acts as that part, and refuses anything else; a part's guard is known as `<part>#<id>`. Protocol 8: a query is a descriptor of its own (`is: query`, `askers`, §6.6), defined and asked like a command over the same methods. Protocol 10: a principal is a path (`plugin/hydra`, §4), in selectors and `describe`; ids joined to it are `<principal>#<id>`. Protocol 11: no layers, declarations or test marks (their methods, ops and fields are gone); `describe` tells `defaults`; the call a remote owner serves carries its span as `traceparent` (§9.2). Protocol 12: `describe` tells `vocabularies`, the names of the session's (was `namespaces`). Protocol 13: a principal is `kind[/id][@owner]` (§4), as JSON `{kind, id?, owner?}`; an id is one level; `as` names an owner of the session's principal. Protocol 14: a cause's `correlation` is `conversation`, and it may carry `origin` (`{word, by}`, §4). Protocol 15: `apply` takes `built` and `unbuilt` (§6.9, §25.4). These numbers were the protocol before its major was frozen: from then it is major 1, and what came in 15 is the feature `built`.
- **The mirror** keeps a participant's copy of the states from the feed and, given a new client after a lost connection, resumes after the seq it has; a gap sends it back to a snapshot. `synced` is whether it follows the registry now: false when its feed is lost, true again with a snapshot, or at once when the feed resumes in the same epoch (nothing may have happened since). `subscribe(states, facts)` keeps only those (waiting until its feed has their values) and subscribes a new connection again before its feed; then its seq moves only with the ticks it carries, so `reach` does not wait for a write it does not keep. It keeps no facts: `recent` asks the registry, so the answer is the same here and there.

### 14.1 What arrives, and how often

A parlance keeps what is so, not what happened: states are its memory, facts pass by. Across a connection that drops and comes back, each kind of message keeps its own promise.

| Message | Way | Promise |
|---|---|---|
| a state's value | host → participant (feed, mirror) | the value now, never one torn by a tick. Ticks come in seq order, without gap or repeat while they are retained (§12); past that, a snapshot of the values now. Values between are not promised: a state is what it is, not its history |
| a state's value | participant → host | its last value. Written while away, it reaches the new session as it stands when the connection is back; the values in between are not sent |
| a fact | host → participant | at most once, in order with the ticks. After a drop, the facts of the retained ticks come; past them a snapshot says `factsLost: true`, and those facts are gone |
| a fact | participant → host | once, while within the dedup window (§6.3). Said while away, it waits and is sent when back, with its id, so the host drops one it took before the drop. It keeps the last `keepAway` (`join(keepAway:)`, 1000); past them the oldest go and `errors` tells how many (`{op: emit}`, `dropped`) once it is back |
| a call | participant → host | once per id, within the dedup window (§9). An answer lost on the way is `lost`: it may have run; a retry with the id runs it at most once and answers how it ended. A call made while away is `lost` and not sent |
| a call | host → participant (its command) | the handler runs once per call; a connection that drops while it runs fails the call (`its owner did not answer`); the registry does not call again |

In one process every message is delivered as it is committed: a listener that comes later gets a state's value now, and no fact said before it listened (`recent(fact, n)` keeps the last ones to look at, not to deliver).

**A fact that must not be lost** is not a fact. When missing one is wrong (an order paid, a message to answer), its owner keeps it as a state (a keyed state of what waits, removed when it is handled, a command to say it is handled), so a part that comes later or comes back finds it. What must outlive the process the host stores itself: persistence is not the parlance's.
